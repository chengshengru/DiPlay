# 实验性分类新增两个开关 · 开发设计文档

> 分支：`android-4.2.2`（GM C140A / API 17）
> 作者：依 spec-first 流程，先出设计文档，按本文档逐步实现。
> 范围：在「高级 / 实验性」设置卡内新增两个开关，并落地对应业务行为。代码改动严格限制在框架层，不触碰爬虫 / 第三方库。

---

## 1. 背景与目标

DiPlay 当前在「高级（Advanced）」分类下已有 `EXPERIMENTAL_DISPLAY`（标题 *Display (experimental)*）实验性卡片，承载 Harman 全屏、分屏、旋转、侧栏等实验特性。本次新增两个彼此独立、但同属「实验性 / 有风险」性质的开关：

| 序号 | 开关 | 行为目标 | 落点模块 |
| --- | --- | --- | --- |
| ① | **USB 连接页实时日志** | 打开后，CarPlay 投屏等待/连接界面（USB 连接页）底部才显示最近若干行 `xcertplay-usb` 诊断日志覆盖层；默认关（打开前不展示） | `CarPlayHostActivity` 实时诊断覆盖层 |
| ② | **无线连接绕过蓝牙开关配置** | 打开后，发起无线连接时跳过「打开蓝牙」弹框，直接获取车机已连接的 iPhone 蓝牙设备并继续后续无线 CarPlay 流程；默认关 | `DiPlayActivity.choosePhone()` 连接引导 |

两个开关均落在 `EXPERIMENTAL_DISPLAY` 卡片内（复用既有实验性卡，无需新增卡片/分区，[见 §6 备选方案]）。

设计约束（来自 `AGENTS.md`）：
- 实验性设置/卡片标题须带本地化后缀：`(experimental)` / `（实验性）` / `（實驗性）` / `(экспериментально)` / `(експериментально)` / `(تجريبي)`。
- 新设置文案使用 `settings_` 前缀；`SettingsTranslationsTest` 要求所有 `values-*` 语言目录都有该字符串且占位符一致。
- 设置项只能出现在一个分类；`SettingsLayoutPolicyTest` 要求每个 `SettingsSection` 恰好映射一个分类。
- 不修改 `Spiders/*`、`Crawlers/*`、KSPlayer 等第三方实现。

## 2. 架构定位

```
SettingsCategory.ADVANCED
  └─ SettingsSection.EXPERIMENTAL_DISPLAY   (DiPlayActivity.kt:119 / 映射于 :154)
       └─ filteredSection(...) 卡片          (DiPlayActivity.kt:2146-2179)
            ├─ Harman 全屏
            ├─ 分屏 / 旋转 / 侧栏
            ├─ ★ ① USB 连接页实时日志        (新增 toggle)
            └─ ★ ② 无线连接绕过蓝牙开关配置  (新增 toggle)
```

- 两个开关均为普通 `toggle(...)`（见 `DiPlayActivity.kt:5625`），**无需重连**：
  - ① 仅控制覆盖层显隐，下次 CarPlay 窗口 / `updateDebugOverlays()` 即生效；
  - ② 仅影响后续连接引导逻辑，下一次发起无线连接时读取。
- 两者**不要**调用 `markReconnectNeeded()` / `reconnectIfRunning()`，避免误断正在运行的会话。

```kotlin
private const val KEY_USB_REALTIME_LOG = "usb_realtime_log"
// 实验性：无线连接绕过"打开蓝牙"弹框，直接使用车机已连接 iPhone（默认关）。

```

### 4.2 新增 load/save 方法（建议放在 `loadDebugLogsEnabled` 之后，约 `:452` 之后）

```kotlin
/** 实验性：USB 连接页实时日志覆盖层；默认关，打开后 CarPlayHostActivity 才渲染诊断行。 */
fun loadUsbRealtimeLog(context: Context): Boolean =
    context.getSharedPreferences(PREFS, Context.MODE_PRIVATE)
        .getBoolean(KEY_USB_REALTIME_LOG, false)

fun saveUsbRealtimeLog(context: Context, enabled: Boolean) {
    context.getSharedPreferences(PREFS, Context.MODE_PRIVATE).edit()
        .putBoolean(KEY_USB_REALTIME_LOG, enabled).apply()
}

/** 实验性：无线连接绕过蓝牙开关配置；默认关，打开后跳过"打开蓝牙"弹框并续接已连接 iPhone。 */
fun loadWirelessSkipBluetoothConfig(context: Context): Boolean =
    context.getSharedPreferences(PREFS, Context.MODE_PRIVATE)
        .getBoolean(KEY_WIRELESS_SKIP_BT_CONFIG, false)

fun saveWirelessSkipBluetoothConfig(context: Context, enabled: Boolean) {
    context.getSharedPreferences(PREFS, Context.MODE_PRIVATE).edit()
        .putBoolean(KEY_WIRELESS_SKIP_BT_CONFIG, enabled).apply()
}
```

### 5.2 无线连接绕过逻辑（位置：`choosePhone()` `:5113-5156`）

`choosePhone()` 现有流程（关键片段，当前 `:5134-5143`）：

```kotlin
val candidates = if (devices.isEmpty() && connectedIphone != null) listOf(connectedIphone) else devices
if (candidates.isEmpty()) {
    if (!adapter.isEnabled) {
        showTurnOnBluetoothDialog(adapter); return
    }
    AlertDialog.Builder(this).setTitle(getString(R.string.pair_your_iphone))
        .setMessage(getString(R.string.on_your_iphone_open_settings_bluetooth_and_pair_with_the_c))
        .setPositiveButton(getString(R.string.open_bluetooth)) { _, _ -> openSystem(Intent(Settings.ACTION_BLUETOOTH_SETTINGS)) }
        .setNegativeButton(getString(R.string.got_it), null).show(); return
}
```

#### 5.2.1 改动 A — 已连接 iPhone 直接续接（插在 `:5132` 的 `Log.i(...)` 之后、`Plan A 兜底` 候选计算 `:5133` 之前）

```kotlin
// 实验性②：绕过蓝牙开关配置。若已探测到车机已连接的 iPhone，跳过"打开蓝牙"弹框与设备选择，
// 直接保存并续接无线流程（应对 API 17 上 adapter.isEnabled 误报关闭的场景）。
if (AirPlayPersistence.loadWirelessSkipBluetoothConfig(this)) {
    val skipDevice = BluetoothCompat.findConnectedIphone(adapter)
    if (skipDevice != null) {
        DiPlayPreferences.savePhone(this, skipDevice.address, skipDevice.name ?: "iPhone")
        val start = pendingWireless; pendingWireless = false
        render()
        if (start) connect(true)
        return
    }
}
```

> 说明：`findConnectedIphone(adapter)` 返回 `BluetoothDevice?`（定义见 `shared/src/main/java/com/shilapi/xcertplay/compat/BluetoothCompat.kt:183`），通过 ACL 真实连接态判定，不依赖 `adapter.isEnabled`，正好规避「BT isEnabled 假阳性」。此分支在 `candidates` 计算之前 return，因此当已连接 iPhone 可探测时，既跳过弹框也跳过设备选择列表。

#### 5.2.2 改动 B — 无可用已连接设备时仅跳过「打开蓝牙」弹框（替换原 `:5135-5143` 整段）

将「`candidates` 为空且蓝牙关闭 → 弹『打开蓝牙』」这一判定与「配对引导」合并，使绕过开关开启时永不弹『打开蓝牙』：

```kotlin
if (candidates.isEmpty()) {
    // 实验性②：绕过蓝牙开关配置时，即使 adapter.isEnabled 误报关闭也不弹"打开蓝牙"，降级为系统蓝牙配对引导。
    val bluetoothOff = !adapter.isEnabled && !AirPlayPersistence.loadWirelessSkipBluetoothConfig(this)
    if (bluetoothOff) {
        showTurnOnBluetoothDialog(adapter); return
    }
    AlertDialog.Builder(this).setTitle(getString(R.string.pair_your_iphone))
        .setMessage(getString(R.string.on_your_iphone_open_settings_bluetooth_and_pair_with_the_c))
        .setPositiveButton(getString(R.string.open_bluetooth)) { _, _ -> openSystem(Intent(Settings.ACTION_BLUETOOTH_SETTINGS)) }
        .setNegativeButton(getString(R.string.got_it), null).show(); return
}
```

- 绕过关闭 + 蓝牙真的关：`bluetoothOff = true` → 原「打开蓝牙」弹框（行为不变）。
- 绕过开启（无论蓝牙是否误报关）：`bluetoothOff = false` → 走系统蓝牙配对引导弹框，**不再弹「打开蓝牙」**。
- 复用既有字符串 `pair_your_iphone` / `on_your_iphone_open_settings_bluetooth_and_pair_with_the_c` / `open_bluetooth` / `got_it`，无新增。

## 6. USB 实时日志覆盖层（CarPlayHostActivity.kt）

覆盖层 `usbDiagView` 已在 `:1622-1639` 构建并 `addView` 到 `root`（`FrameLayout` 底部），目前显隐由 `updateDebugOverlays()` 统一控制。

### 6.1 修改 `updateDebugOverlays()`（`:5720-5725`）

当前：

```kotlin
private fun updateDebugOverlays() {
    statusScrollView?.visibility = View.GONE
    val waitingVisible = activeScreenStreamTypes.isEmpty()
    connectionPanel?.visibility = if (waitingVisible) View.VISIBLE else View.GONE
    usbDiagView?.visibility = if (waitingVisible) View.VISIBLE else View.GONE
}
```

改为（按 ① 开关门控；默认关 → 不展示）：

```kotlin
private fun updateDebugOverlays() {
    statusScrollView?.visibility = View.GONE
    val waitingVisible = activeScreenStreamTypes.isEmpty()
    connectionPanel?.visibility = if (waitingVisible) View.VISIBLE else View.GONE
    // 实验性①：仅当开关打开且处于等待/连接屏时显示 USB 实时诊断日志覆盖层。
    usbDiagView?.visibility = if (waitingVisible && AirPlayPersistence.loadUsbRealtimeLog(this)) View.VISIBLE else View.GONE
}
```

### 6.2 生效时机

- `updateDebugOverlays()` 在投屏构建（`:1715`）、连接态变化（`:682`、`:2956`、`:3227`、`:4819`、`:5354`、`:5434`、`:5690`、`:5717` 等）多处调用，开关读取实时生效。
- 用户在设置页切开关 → 返回投屏：下次 `updateDebugOverlays()` 触发即应用。
- **可选增强（推荐）**：在 `CarPlayHostActivity` 注册 `OnSharedPreferenceChangeListener` 监听 `KEY_USB_REALTIME_LOG`，变化时主动调 `updateDebugOverlays()`，实现「设置页切开关、投屏立即显隐」的实时反馈。实现方式参照 `AirPlayPersistence.observeClusterSpeedometer`（`:813-820`），新增 `observeUsbRealtimeLog(context, changed)` 或在 `CarPlayHostActivity` 内直接监听 `xcertplay_airplay` 该 key。本次基线实现以「下次 updateDebugOverlays 生效」为准，可选增强单独提交。

### 8.1 新增 `ExperimentalTogglesSettingsTest.kt`（仿 `SystemBarSettingsTest.harmanFullscreenIsOptInAndInAdvancedSettings` `:90-109`）

```kotlin
package com.shilapi.xcertplay

import android.content.Intent
import androidx.test.core.app.ApplicationProvider
import com.shilapi.xcertplay.AirPlayPersistence
import org.junit.Assert.assertFalse
import org.junit.Assert.assertTrue
import org.junit.Before
import org.junit.Test
import org.junit.runner.RunWith
import org.robolectric.Robolectric
import org.robolectric.RobolectricTestRunner
import org.robolectric.Shadows.shadowOf

@RunWith(RobolectricTestRunner::class)
class ExperimentalTogglesSettingsTest {
    private lateinit var activity: DiPlayActivity

    @Before fun setUp() {
        AirPlayPersistence.saveUsbRealtimeLog(ApplicationProvider.getApplicationContext(), false)
        AirPlayPersistence.saveWirelessSkipBluetoothConfig(ApplicationProvider.getApplicationContext(), false)
        activity = Robolectric.buildActivity(
            DiPlayActivity::class.java,
            Intent(ApplicationProvider.getApplicationContext(), DiPlayActivity::class.java).putExtra("page", "settings"),
        ).setup().get()
    }

    @Test fun usbRealtimeLogIsOptInAndInAdvanced() {
        openAdvanced()
        val sw = switches().single { it.contentDescription == activity.getString(R.string.settings_usb_realtime_log) }
        assertFalse(sw.isChecked)
        sw.performClick()
        assertTrue(sw.isChecked)
        assertTrue(AirPlayPersistence.loadUsbRealtimeLog(activity))
    }

    @Test fun wirelessSkipBluetoothIsOptInAndInAdvanced() {
        openAdvanced()
        val sw = switches().single { it.contentDescription == activity.getString(R.string.settings_wireless_skip_bluetooth_config) }
        assertFalse(sw.isChecked)
        sw.performClick()
        assertTrue(sw.isChecked)
        assertTrue(AirPlayPersistence.loadWirelessSkipBluetoothConfig(activity))
    }

    private fun openAdvanced() {
        descendants(activity.window.decorView)
            .single { it.contentDescription == activity.getString(R.string.settings_open_category, activity.getString(R.string.settings_advanced)) }
            .performClick()
    }

    private fun switches() = descendants(activity.window.decorView).filterIsInstance<androidx.appcompat.widget.SwitchCompat>()
    private fun descendants(view: android.view.View) = androidx.test.espresso.util.TreeIterables.breadthFirstViewTraversal(view).toList()
}
```

## 9. 风险与回滚

| 风险 | 等级 | 说明 / 缓解 |
| --- | --- | --- |
| ② 绕过逻辑在「无已连接 iPhone」时仅降级为配对引导，未自动续接 | 低 | 符合预期兜底；若车机确实已连 iPhone 但 `findConnectedIphone` 因 API 17 限制探测不到，仍会落到配对引导（不弹「打开蓝牙」），用户可手动完成 |
| ② 在蓝牙真关且未配对时跳过弹框，用户可能困惑 | 低 | 降级为系统蓝牙配对引导弹框，文案已说明去系统蓝牙设置配对 |
| ① 覆盖层遮挡投屏底部内容 | 低 | 仅 `maxLines=12`、半透明黑底、位于等待/连接屏（无视频流时）才显示；默认关 |
| 翻译缺失导致 `SettingsTranslationsTest` 失败 | 中 | 严格按 §7 补齐 7 目录 4 键；CI 会拦截 |
| 误改 `EXPERIMENTAL_DISPLAY` 既有开关 | 低 | 新增插入位置明确（sidePanel 之后），不影响既有行 |

回滚：两个开关均为独立 `KEY_` + 独立 UI 行，删除对应 `toggle` 两行、`choosePhone` 两处改动、`updateDebugOverlays` 一行及 `AirPlayPersistence` 4 方法 + 2 常量即可整体回退，无数据库迁移。

## 11. 备选方案

- **独立实验性卡片**：若不愿把连接/诊断类开关塞进 `Display (experimental)` 卡，可在 `SettingsSection` 枚举（`:106`）新增 `EXPERIMENTAL_FEATURES`，在 `sectionsByCategory`（`:152`）映射到 `ADVANCED`，并在 `allSettingsSections()` 内用 `filteredSection(...)` 新建卡片（标题如 `Experimental features (experimental)`，需额外 1 个 `settings_*` 卡标题字符串进 7 目录）。代价：多 1 个翻译键 + 需确认 `SettingsLayoutPolicyTest` 仍通过（单分类映射即可）。
- 本文档主方案选择「复用 `EXPERIMENTAL_DISPLAY` 卡」，改动最小、翻译键最少、对既有测试零影响，推荐先行。
