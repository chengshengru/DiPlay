## 真机崩溃修复：有线 CarPlay USB 描述符 API 21+ 直调（API 17 真机 crash-last.log）
- 现象：GM C140A（android 4.2.2 / sdk 17）插 iPhone 授权瞬间进程崩溃：
  `NoSuchMethodError: android.hardware.usb.UsbDevice.getConfigurationCount at IphoneCarPlayConfiguration.find(:31)`
  ← CarPlayController.onIphonePermission(:1875) ← IphoneUsbHost$registerPermissionReceiver$1.onReceive（广播接收器，无 try/catch）。
- 根因：有线路径整条链路用了 API 21+ 符号（`UsbConfiguration` 类本身、`UsbDevice.getConfigurationCount/getConfiguration`、
  `UsbInterface.getAlternateSetting`、`UsbDeviceConnection.setConfiguration/setInterface`），dalvik 校验器把无法解析的调用换成抛异常桩，
  一执行即 NoSuchMethodError。同一路径共 5 处，修完第一处会接着崩第二处。
- 事实核查（AOSP android-4.2.2_r1 源码）：API 17 无 `UsbConfiguration`；`UsbInterface` 无 `getAlternateSetting()`；
  JNI 把**所有 configuration 的 interface** 平铺成一个数组给 `UsbDevice.getInterfaceCount()/getInterface()`；
  `UsbDeviceConnection.controlTransfer(..., null, 0, timeout)` 无 checkBounds（可发 0 长度标准请求）。
- 修复：新增 `shared/.../compat/UsbDescriptorCompat.kt`（`UsbConfigurationView` + 4 个 API 17 安全 helper）：
  - `configurations(device)`：21+ 走真实 `UsbConfiguration`；17-20 把平铺 interface 按"接口号回绕"切回 configuration；
  - `selectConfiguration`：21+ 走 `setConfiguration`；17-20 走标准 SET_CONFIGURATION 控制传输（bConfigurationValue 从 `rawDescriptors` 解析）；
  - `selectInterface`：21+ 走 `setInterface`；17-20 走标准 SET_INTERFACE 控制传输；
  - `alternateSetting`：21+ 真值；17-20 返回 -1（该版本不携带该字段，不再误报 0）。
- 收编调用点：`IphoneCarPlayConfiguration`（改用 view）、`NcmFunctionDiscovery`、`IphoneUsbHost`（setConfiguration/describeAll）、
  `NcmUsbBridge`（setInterface + 3 处日志）、`CarPlayController`（2 处日志）。另给 `onIphonePermission` 加 try/catch → `fail(error)`，
  避免广播接收器里任何异常再直接杀进程。
- 验证：`:shared:compileDebugKotlin` ✓、新单测 `UsbDescriptorCompatTest`（5 例）+ 既有 `UsbSetupDiagnosticsTest` ✓、
  `:shared:assembleDebug :mobile:assembleDebug` ✓。未提交。
- 遗留风险：API 17 无法读 alt setting，NCM 数据口靠 SET_INTERFACE 控制传输兜底；真机需复验 `xcertplay-usb` 日志里的
  `legacy SET_CONFIGURATION` / `legacy SET_INTERFACE` 两行是否 read>=0。

## 不弹"信任"/卡连接界面：重枚举静默挂起根因与 watchdog 修复
- 现象（API 17 真机，前两轮修复崩溃/非 API17 调用后）：授权"允许"后 iPhone 无任何反应、车机停在 CarPlay 连接界面、无报错。
- 根因分析结论：所有下游阶段都有超时（`Iap2UsbMuxHost.awaitConnected`、`PAIR_TIMEOUT_MILLIS=5min`、`VPN_CONNECT_TIMEOUT`、
  `CONTROL_LOOP_TIMEOUT` 等），唯独 `WaitingForReenumeration` **无超时、无报错路径**。iPhone 的 0x52 CarPlay 请求常**原地切换活动
  USB 配置而不触发总线重枚举**，或随之的 `ACTION_USB_DEVICE_ATTACHED` 广播未被动态注册的接收器捕获 → 控制器永久停在该状态。
  匹配"无报错、iPhone 无反应、卡连接界面"全部特征。`iphoneDevices` 默认空 → `appleVendor()` 仅按厂商 0x05ac 匹配，排除 matcher 漏检。
- 修复（`CarPlayController.kt`，沿用既有诊断钩子 `connectionDiagnostic` → 屏幕底部实时覆盖层 + logcat）：
  - 新增状态：`reenumerationGeneration`（AtomicInteger 守卫，避免重枚举成功后 watchdog 误触发）、`lastIphoneDevice`（兜底重试/探测）。
  - `beginReenumeration` 进入 `WaitingForReenumeration` 后调用 `scheduleReenumerationWatchdog()`（5s：`REENUMERATION_WATCHDOG_MILLIS`）。
  - 新增 `recoverFromReenumeration()`：超时后直接扫 `UsbManager.deviceList`（不依赖 PID 白名单 matcher）找 Apple 设备；
    若已暴露 CarPlay 配置且有权限→`openDataPaths`；有配置无权限→`requestIphonePermission`（补弹二次授权）；
    配置仍缺且未达 `MAXIMUM_REENUMERATION_ATTEMPTS(=2)`→`retryReenumerationOrFail` 重试 0x52；否则 `fail` 明确报错。
  - `checkIphoneAvailability` 也记 `lastIphoneDevice`。
- 注意：若 iPhone 为真·原地配置切换（Android 缓存描述符陈旧），`find()` 仍返 null → 重试 0x52 两次后仍 fail 并明确报错（不再静默挂起），
  诊断覆盖层会显示 `reenumeration watchdog: ... configReady=...` 最后一行，便于用户确认是哪种卡点。
- 验证：`:shared:compileDebugKotlin :common:compileDebugKotlin` ✓（仅既有 deprecation 警告）、`:mobile:assembleDebug` ✓（APK 已重产）。未提交。
- 待用户侧载新 APK 复验：看屏幕底部实时诊断末行是 `reenumeration watchdog: configReady=true`（→ 直接继续）/ `configReady=false…重试`
  / `重枚举后 iPhone 仍未暴露 CarPlay USB 配置`，据此决定下一步（原地切换则需另寻强制 setConfiguration 时机，或二次授权被系统吞掉）。

## 无线连接卡"打开蓝牙"死循环：方案 A 改造（adapter.isEnabled 误报绕过）
- 现象：车机无线连接时弹"打开蓝牙"→跳系统设置，但系统不让开（开了自动关），实际蓝牙已开、iPhone 显示"已连接"。
- 根因：无线链路门禁只信 `adapter.isEnabled()`，车机蓝牙开关状态与无线电实态不同步（误报 false）即死循环。蓝牙在无线 CarPlay 里仅做 iAP2 RFCOMM 引导（传 Wi-Fi 凭据），数据传输走 Wi-Fi/mDNS，故"已连接 iPhone"才是无线电可用的铁证。
- 方案 A 改动（6 处，均保持零警告、框架层、未触碰爬虫）：
  1. `shared/.../compat/BluetoothCompat.kt`：新增 `isDeviceConnected(device)`（反射 `BluetoothDevice.isConnected`，API 1 方法，catch 仅列 API 1 异常以过 API 17 验证器）+ `findConnectedIphone(adapter)`（已配对 iPhone 中筛唯一真实 ACL 已连接者，歧义/无则返 null 不抛）。
  2. `orchestration/CarPlayController.kt`：新增 import；门禁 1337-1357 改为先 `probeConnectedWirelessIphone(adapter)`，`!adapter.isEnabled && link==null` 才抛错，`!bluetoothRecoveryComplete && link==null` 才抛错，`device = link ?: selectWirelessBluetoothDevice(adapter)`；新增 `probeConnectedWirelessIphone`（优先 `BluetoothCompat.findConnectedIphone`，退化到 profile 连接判定）；门禁后补一行 Plan A 诊断日志（adapterEnabled/recoveryComplete/connectedIphone/bypassGate）。
  3. `common/.../DiPlayActivity.kt`：新增 import；`choosePhone()` 改为 adapter==null 或无"已连接 iPhone"且 isEnabled==false 才弹"打开蓝牙"；提取 `showTurnOnBluetoothDialog()` 复用；候选列表兜底：bondedDevices 为空但已探测到连接 iPhone 时纳入候选，确保用户能点选已连接 iPhone。

## 0.2.17-api17 真机诊断捕获：重枚举 watchdog 静默（挂死约 6 分钟）
- 文件：`Desktop/DiPlay-20261011-170427-120.txt`（GM C140A / API 17 / 0.2.17-api17；当前会话 diplay.log pid 2872，16:56–17:02）。
- 证明项（证据级）：
  1. 部署 APK 已含重枚举+watchdog 代码——出现 CarPlayController.kt:2948 `STEP usb/reenum` 与 :1975 `USB transition requested count=1`。
  2. iPhone 接受了 0x52 配置请求（transferred==1 才回 ReenumerationRequested，IphoneUsbHost.kt:161-169），排除锁屏拒请求。
  3. IphoneCarPlayConfiguration.find() 授权时及之后恒返 null（USB configuration ready=false configurationId=none，:1911-1919），iPhone 未向主机暴露 CarPlay 配置（USBMUX 0xff/0xfe/0x02 + CDC-NCM 0x02/0x0d 匹配，IphoneCarPlayConfiguration.kt:34-45）。
  4. 5s watchdog（REENUMERATION_WATCHDOG_MILLIS=5_000）在 6 分钟挂死期间零日志——recoverFromReenumeration 每个分支都打 reenumeration watchdog: ...（:2009/2015/2022/2026/2030），却一行没有；且无 count=2 重试。
- 关键新发现：唯一能吞掉所有分支且不产生 count=2 的是 :1997 守卫 `if (closed || phase != REENUMERATION || generation mismatch) return`。teardown 日志 phase 仍 REENUMERATION、generation 稳定（无 count=2）-> closed 在 5s 回调前已被置 true。但 start()(:460-463) 遇 closed 直接 return，故新 attempt 不能以 closed 启动 -> closed 是在重枚举等待窗口内被 close()(:634-637) 置位（最可能 Activity onStop 或上一 attempt teardown 与当前 attempt 竞态）。此后所有 mainHandler 恢复逻辑因 closed 守卫静默 no-op，而 in-flight 状态日志（不查 closed）继续打印 -> 卡连接界面、无报错。
- 结论：上一轮 watchdog 补丁因 closed 守卫被自身生命周期关闭而失效。修复方向（待确认是否实施）：(1) watchdog 守卫去掉 closed；(2) 守卫前加诊断日志确认触发/bail 原因；(3) 重枚举恢复主动轮询 usbManager.deviceList（recoverFromReenumeration 已有扫描逻辑但需先能运行），不依赖 ATTACHED 广播（Apple 0x52 后常原地切配置、无新 ATTACHED 广播，GM C140A 固件确未送达）；(4) 确认 close() 在重枚举期被谁调用。
- 已确认修复项：早期 getConfigurationCount (API17/NoSuchMethodError) 在当前构建已不复现，UsbDescriptorCompat 兜底生效，非本次问题。

## 根因修正：0x52 重枚举触发方向错误（IN→OUT），iPhone 才会真的切 CarPlay 配置
- 用户澄清：iPhone 当时"无任何反应"。推翻上一条"iPhone 接受了 0x52 请求"的判断——那个 transferred==1 只是对一次
  IN（0xc0 设备→主机）读请求的 USB 层 ACK，并非 iPhone 执行了重枚举命令。
- 协议事实：Apple 私有请求 0x52 真正命令 iPhone 切换 CarPlay 配置并重枚举的是 **OUT（0x40 主机→设备、wValue=0、wIndex=4、
  1 字节负载 0x01）**；原代码发的是 IN 读 1 字节，iPhone 只回状态字节、根本没被命令切换，故"无反应、配置永不出现"。
- 修复（均框架层，未碰爬虫）：
  1. `IphoneUsbHost.kt`：companion 新增 `USB_VENDOR_DEVICE_OUT=0x40` 与 `CARPLAY_CONFIGURATION_ENABLE=0x01`；
     `requestCarPlayReenumerationAsync` 改发 OUT 写 0x01（原 IN 读），且每次请求落一行诊断
     `CarPlay reenumeration request dir=OUT bRequest=0x52 wIndex=0x4 transferred=$t`（下一步真机复验即见 iPhone 是否真重枚举）。
  2. `CarPlayController.kt`：
     - `scheduleReenumerationWatchdog` 守卫去掉 `closed`（恢复逻辑职责就是救"卡住但没被主动关闭"的连接，被生命周期 close 误伤后仍需兜底）。
     - `recoverFromReenumeration` 开头固定打一行 `reenumeration watchdog fired: phase=.. closed=.. attempts=..`，确保 watchdog 永不再静默。

  `:shared:compileDebugKotlin` + 真机复验（看诊断末行 `CarPlay reenumeration request dir=OUT` 与 `reenumeration watchdog fired` 是否出现、
  iPhone 是否出现 CarPlay 界面）。未提交。
