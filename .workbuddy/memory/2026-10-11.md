## 真机崩溃修复：有线 CarPlay USB 描述符 API 21+ 直调（API 17 真机 crash-last.log）
- 现象：GM C140A（android 4.2.2 / sdk 17）插 iPhone 授权瞬间进程崩溃：
  `NoSuchMethodError: android.hardware.usb.UsbDevice.getConfigurationCount at IphoneCarPlayConfiguration.find(:31)`
  ← CarPlayController.onIphonePermission(:1875) ← IphoneUsbHost$registerPermissionReceiver$1.onReceive（广播接收器，无 try/catch）。
- 根因：有线路径整条链路用了 API 21+ 符号（`UsbConfiguration` 类本身、`UsbDevice.getConfigurationCount/getConfiguration`、
  `UsbInterface.getAlternateSetting`、`UsbDeviceConnection.setConfiguration/setInterface`），dalvik 校验器把无法解析的调用换成抛异常桩，
  一执行即 NoSuchMethodError。同一路径共 5 处，修完第一处会接着崩第二处。
- 事实核查（AOSP android-4.2.2_r1 源码）：API 17 无 `UsbConfiguration`；`UsbInterface` 无 `getAlternateSetting()`；
  JNI 把**所有 configuration 的 interface** 平铺成一个数组给 `UsbDevice.getInterfaceCount()/getInterface()`；
  `UsbDeviceConnection.controlTransfer(..., null, 0, timeout)` 无 checkBounds（可发 0 长度标准请求）。
- 修复：新增 `shared/.../compat/UsbDescriptorCompat.kt`（`UsbConfigurationView` + 4 个 API 17 安全 helper）：
  - `configurations(device)`：21+ 走真实 `UsbConfiguration`；17-20 把平铺 interface 按"接口号回绕"切回 configuration；
  - `selectConfiguration`：21+ 走 `setConfiguration`；17-20 走标准 SET_CONFIGURATION 控制传输（bConfigurationValue 从 `rawDescriptors` 解析）；
  - `selectInterface`：21+ 走 `setInterface`；17-20 走标准 SET_INTERFACE 控制传输；
  - `alternateSetting`：21+ 真值；17-20 返回 -1（该版本不携带该字段，不再误报 0）。
- 收编调用点：`IphoneCarPlayConfiguration`（改用 view）、`NcmFunctionDiscovery`、`IphoneUsbHost`（setConfiguration/describeAll）、
  `NcmUsbBridge`（setInterface + 3 处日志）、`CarPlayController`（2 处日志）。另给 `onIphonePermission` 加 try/catch → `fail(error)`，
  避免广播接收器里任何异常再直接杀进程。
- 验证：`:shared:compileDebugKotlin` ✓、新单测 `UsbDescriptorCompatTest`（5 例）+ 既有 `UsbSetupDiagnosticsTest` ✓、
  `:shared:assembleDebug :mobile:assembleDebug` ✓。未提交。
- 遗留风险：API 17 无法读 alt setting，NCM 数据口靠 SET_INTERFACE 控制传输兜底；真机需复验 `xcertplay-usb` 日志里的
  `legacy SET_CONFIGURATION` / `legacy SET_INTERFACE` 两行是否 read>=0。

## 不弹"信任"/卡连接界面：重枚举静默挂起根因与 watchdog 修复

  - 新增 `recoverFromReenumeration()`：超时后直接扫 `UsbManager.deviceList`（不依赖 PID 白名单 matcher）找 Apple 设备；

## 根因修正：0x52 重枚举触发方向错误（IN→OUT），iPhone 才会真的切 CarPlay 配置
- 用户澄清：iPhone 当时"无任何反应"。推翻上一条"iPhone 接受了 0x52 请求"的判断——那个 transferred==1 只是对一次
  IN（0xc0 设备→主机）读请求的 USB 层 ACK，并非 iPhone 执行了重枚举命令。
- 协议事实：Apple 私有请求 0x52 真正命令 iPhone 切换 CarPlay 配置并重枚举的是 **OUT（0x40 主机→设备、wValue=0、wIndex=4、
  1 字节负载 0x01）**；原代码发的是 IN 读 1 字节，iPhone 只回状态字节、根本没被命令切换，故"无反应、配置永不出现"。
- 修复（均框架层，未碰爬虫）：

     `requestCarPlayReenumerationAsync` 改发 OUT 写 0x01（原 IN 读），且每次请求落一行诊断
     `CarPlay reenumeration request dir=OUT bRequest=0x52 wIndex=0x4 transferred=$t`（下一步真机复验即见 iPhone 是否真重枚举）。
  2. `CarPlayController.kt`：
     - `scheduleReenumerationWatchdog` 守卫去掉 `closed`（恢复逻辑职责就是救"卡住但没被主动关闭"的连接，被生命周期 close 误伤后仍需兜底）。

## 【更正】第99-114节"OUT 正确"假设已被证伪——0x52 正确方向是 IN（0xc0）
- 第99-114节基于"iPhone 无反应"推断 OUT(0x40 写 0x01) 才对，该推断**错误**，现以两份硬证据推翻：
  1. **真机日志（用户截图）**：OUT 请求 `transferred=-1` —— 这是 iPhone 对控制传输的**显式拒绝**（写入零字节或非法请求被 stall），被拒绝的请求绝不可能触发切换。
  2. **上游 LIVI 源码取证**（WebFetch `github.com/f-io/LIVI` `native/livi-helperd/crates/iap2-usbmux/src/linux.rs`）：
     `request_carplay_configs` 用 `device.control_in(ControlIn{control_type:Vendor, recipient:Device, request:0x52, value:0x0000, index:0x0004, length:1})`
     —— 即 **bmRequestType=0xc0（设备→主机 IN）、读 1 字节**，wIndex=4 选 CarPlay 配置集。随后 `ensure_carplay_config`
     轮询 `bNumConfigurations` 直到达到 `CP_CONFIG=6`，再 `fs::write(bConfigurationValue,"6")` 显式 SET_CONFIGURATION(6)。
  3. **真机 IN 测试**（0.2.17-api17，内存第88-97节）：IN `transferred==1`（iPhone 接受 setup 包）。OUT 被拒、IN 被受——方向只能是 IN。
- 已落实修复（`IphoneUsbHost.kt`）：
  - `requestCarPlayReenumerationAsync` 回退为 `controlTransfer(USB_VENDOR_DEVICE_IN=0xc0, 0x52, 0, 0x0004, 1字节buffer, 1s)`，
    与 LIVI `control_in` 完全一致；诊断落 `CarPlay reenumeration request dir=IN bRequest=0x52 wIndex=0x4 transferred=$t`。
  - 移除因 OUT 假设新增的死常量 `USB_VENDOR_DEVICE_OUT=0x40` 与 `CARPLAY_CONFIGURATION_ENABLE=0x01`（已 grep 确认无引用）。
- **关键再判定**：第88-97节"IN 后 find() 恒返 null"**并非方向问题**，而是 Android 车机对 iPhone 重枚举后的描述符刷新/ATTACHED
  广播处理不可靠（GM C140A 固件确未可靠送达广播，见第96节）。即 0x52 IN 已正确触发 iPhone 重枚举，但主机侧没拿到新配置。
  - 此问题已由"不依赖 closed 的 watchdog"缓解：`scheduleReenumerationWatchdog`（去掉 closed 守卫）5s 后触发
    `recoverFromReenumeration`，直接扫描 `UsbManager.deviceList` 按 `vendorId==0x05ac`（不依赖 PID 白名单）找重枚举后的 Apple 设备，
    再 `IphoneCarPlayConfiguration.find()`；找到即 `openDataPaths`（→ `openIap2UsbSession` → `selectConfiguration` 发 SET_CONFIGURATION）。
