# 2026-10-13 DiPlay 蓝牙弹窗第五轮：真根因 = manifest 缺 BLUETOOTH 权限

## 决定性证据（0.2.18-api17 真机截图）
- 弹的是「配对 iPhone」弹窗（choosePhone 5137 分支）而非「打开蓝牙」→ adapter 非 null、isEnabled=true，但 bondedDevices 空 + 探针 null。

## 根因
- common/AndroidManifest.xml 完全没有 `android.permission.BLUETOOTH` / `BLUETOOTH_ADMIN`（shared 只有 API 31+ 的 BLUETOOTH_CONNECT，API 17 无效）。
- API 17 上 `bondedDevices`/`device.name`/`isConnected` 反射都需要 BLUETOOTH 权限 → SecurityException → 被代码 `runCatching{}.getOrDefault(emptyList())` 静默吞掉 → 配对列表恒空。
- getDefaultAdapter()/isEnabled 不需要权限，所以之前 adapter/开关判断全部正常，掩盖了权限缺失。
- 结论：车机蓝牙一直正常，是 App 自己读不到配对数据。

## 修复
1. common/AndroidManifest.xml 加 `BLUETOOTH` + `BLUETOOTH_ADMIN`（API ≤30 安装期自动授予）。
2. choosePhone 的「配对 iPhone」弹窗也 UI 化诊断（isEnabled/bonded 数/异常类型/connectedIphone），bondedResult 保留 exceptionOrNull 不再静默吞。
3. 确认 mobile manifest 无权限 remove，merge 安全。

## 复验
- 重建侧载后点"选择 iPhone"：预期直接列出已配对设备（含已连接 iPhone）。
- 若仍空：新诊断会显示"配对列表读取失败: <异常类型>"，截图即可继续定位。

# 2026-10-13 有线 CarPlay 第三轮：根因 = API 17 配置分组/配置值靠猜，切到了错误的配置

## 决定性证据（0.2.18-api17 真机屏幕诊断截图）
- `ERROR Android could not claim USBMUX interface 1 (active=5 deviceIfaces=[…])`，attempt=15 → 确定性失败，不是 #518 竞态。
- **`active=5`**：LIVI 的 CarPlay 配置是 **6**（`CP_CONFIG=6`）→ 切完却是 5，说明切换目标值根本不是配置 6。
- 平铺接口列表里 NCM 函数在 4~7 号（`2.d.0`/`a.0.1`），而 claim 的是 1 号 → 内核 usbfs 对
  `ifnum >= actconfig->desc.bNumInterfaces` 或 `interface[ifnum]==NULL` 直接 ENODEV。

## 根因
`UsbDescriptorCompat.legacyConfigurations`（API 17-20）此前只用"接口号回落"启发式切分平铺接口列表，
`UsbConfigurationView.id` 恒为 `UNKNOWN(-1)`，切换目标值改用 `configurationValues()[index]` **按序号猜**：
1. 接口号在各配置之间都从 0 重新开始，**单接口配置**（只有 0 号）接在上一个以 0 结尾的配置之后时不会回落
   → 两个配置被并成一个，后续序位全部错位；
2. `find()` 因此可能选中错误的合成配置，`target` 取到错误值（5 而非 6），`usbMux` 取到别的配置里的接口（id=1）；
3. iPhone 被切到错误配置，该配置里没有 1 号接口 → claim 失败（与 `active=5` 自洽）。

## 修复（只动框架层，未碰爬虫）
1. `UsbDescriptorCompat`：新增 `descriptorConfigurations(rawDescriptors)` 从 raw descriptors 精确解析
   每个配置的 bConfigurationValue + 接口号顺序；`legacyConfigurations` 优先用它，并要求
   `sum(接口数)==device.interfaceCount` 且逐配置接口号序列一致，否则回退旧启发式。→ `id` 变成真实配置值。
2. `IphoneCarPlayConfiguration`：新增 `usbMuxCandidates(device, config)`（跨配置的全部 ff/fe/02 接口，按 `id:端点数` 去重）。
3. `IphoneUsbHost`：`claimUsbMuxInterface` 逐个候选尝试（首个 claim 成功且带 bulk 端点者胜）；
   `probeClaimableInterfaces`（claim 全失败时一次性逐个接口号探针）；`selectConfiguration` 现在无条件输出
   屏幕诊断行（含 target/active），切换过程不再对屏幕不可见。
4. 单测：`rawDescriptorsRecoverConfigurationValuesAndInterfaceOrder` / `unusableRawDescriptorsYieldNoConfigurations`。

## 下一步复验判据（侧载后看屏幕）
- `usb config select target=6 ok=true active=6` → 分组修复生效。
- `usbmux claimed iface=<n> attempts=<m>` → 成功进入 iAP2/NCM。
- 若 target=6/active=6 但 claim 仍失败 → 内核 actconfig 未跟随（API 17 无框架 `setConfiguration`），
  看 `claimProbe=[…]`：仅 `0=ok` → actconfig 只识别 1 个接口；多号 ok 而目标号 fail → 目标接口被内核驱动/其他 usbfs 持有者占用。
