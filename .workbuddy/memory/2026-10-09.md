## 车机无 adb 闪退：崩溃日志落盘方案
- 用户痛点：真机（车机）闪退且无法用 adb 连接，拿不到错误。
- 新增 `common/.../CrashFileLogger.kt`：全局 `Thread.setDefaultUncaughtExceptionHandler`，
  崩溃时同步把完整 Java/Kotlin 堆栈写入文件（deviceMeta + stackTrace），保留最近 5 份
  (`crash-<时间戳>.log`) 并维护 `crash-last.log` 稳定指针。
- 在 `DiPlayApplication.onCreate()` 安装（此前该类为空，零侵入）。
- 在 `DiPlayActivity.exportDiagnostics()` 诊断报告内新增 "Last uncaught Java crash" 段，
  把上次崩溃堆栈内联进报告，车机内"保存诊断报告→分享/查看"即可拿到，无需 adb。
- 启动后若上次有崩溃，`onStart` 弹 Toast 提示文件路径（复用 `diagnostic_report_saved_to_path` 字符串，避免新增翻译资源）。
- 文件落点：`Android/data/com.shilapi.xcertplay/files/crash-reports/crash-last.log`
  （external-files 不可用时回退 filesDir）。
- 限制：仅抓 Java 未捕获异常；native(SIGSEGV)/ANR 抓不到（native 由 ProcessExitDiagnostics
  在 Android 11+ 记原因码，无堆栈）。
- 附带修复：`common/AndroidManifest.xml` 补 `tools:overrideLibrary`（与 mobile/automotive
  一致），解决 `:common:testDebugUnitTest` 自身 manifest 合并因 androidx.car.app minSdk23 失败的问题（纯构建期，无运行时影响）。
- 验证：`:common:compileDebugKotlin` BUILD SUCCESSFUL；`CrashFileLoggerTest.kt` 不在编译错误列表。
  注意：本沙箱内 `:common:testDebugUnitTest` 仍有大量**预先存在**的 Robolectric 版本错配
  （ShadowDisplayManager.addDisplay / GraphicsMode 等），与本次改动无关。

## 真机系统版本约束：Android 4.2.2（API 17，无法升级）
- 工程 minSdk=17，故整体兼容。针对本方案逐点复核 API 17 安全性：
  - `resolveDir` 改用 `getExternalFilesDir(null)`(API8)+手动拼 `crash-reports` 子目录，
    避开带类型参数的 `getExternalFilesDir(String)` 在老平台行为不稳的问题（已改）。
  - `Thread.setDefaultUncaughtExceptionHandler` / `Process.killProcess` 均为 API1；
    `Charsets.UTF_8`、`SimpleDateFormat`、`getPackageInfo(pkg,0)`、`Toast` 均 API17 可用。
  - 诊断导出：API17 走 `saveWithoutPicker` 的 external-files/diagnostic-reports 或 filesDir 兜底
    （MediaStore 仅 Q+）；FileProvider(`<external-files-path>`/`<files-path>`)、`ClipData`(API16+)
    在 17 均可用 → 车机内"保存诊断报告→分享/查看"可用。
  - 4.2.2 为经典外部存储模型（无 scoped storage），`crash-reports` 文件夹直接用 USB MTP 或
    车机文件管理器即可拷出，比新 Android 更方便。
- 局限提醒：handler 装在 `Application.onCreate`（multidex 的 `attachBaseContext` 之后），
  故仅能抓到 onCreate 之后的闪退；attachBaseContext 之前（如 multidex 安装期）的极早期崩溃抓不到。
  native(SIGSEGV)/ANR 仍不在范围内。

## 新线索：真机闪退同时"桌面 launcher 也崩"
- 普通 App 的 Java 崩溃只杀自己进程，绝不连累系统 launcher。launcher 一起崩 ⇒ 不是普通 Java 异常。
- 复核 manifest：`common/AndroidManifest.xml` 中 `DiPlayActivity` **只有 `LAUNCHER`，无生效的 `HOME`**
  （grep 命中的 `category.HOME` 在 19-29 行的注释 `<queries>` 块内）。故 DiPlay 不是 manifest 定义的桌面。
  线索指向更高层级：① native 崩溃(SIGSEGV，shared 含 JNI/媒体 so，4.2.2 加载即崩)；
  ② 崩溃波及 system_server（DiPlay 持有 SYSTEM_ALERT_WINDOW/WRITE_SETTINGS/PACKAGE_USAGE_STATS 强权限，
  异常 binder 事务可致 system_server 死→框架重启→连带杀 launcher）；③ 车机把 DiPlay 当常驻/persistent，
  启动期崩被 watchdog 反复拉起→看起来像桌面反复崩（boot loop）。
- **关键结论**：Java `UncaughtExceptionHandler` 抓不到 native/system 级崩溃；且 App UI 一死，
  之前的"诊断报告导出"路径彻底失效（这就是用户"拿不到报错"的真正原因）。
- 加固 `CrashFileLogger` 以应对"App/桌面死了也要拿到日志"：
  1. 处理器安装时机从 `onCreate` 提前到 `attachBaseContext` 且 `super` 之前
     （覆盖 MultiDex.install / 早期类初始化崩溃，最可能是启动期崩溃根因）。
  2. 新增**公共外部路径**副本：`/sdcard/DiPlay/crash-last.log`（4.2.2 无 scoped storage、世界可读，
     App 死了也能用电脑 MTP / 任意文件管理器拷）。
  3. `common/AndroidManifest.xml` 新增 `WRITE_EXTERNAL_STORAGE`（4.2.2 安装期自动授予的普通权限，
     写公共存储必需）。
  4. `mobile/build.gradle.kts` + `mobile/multidex-keep.pro`：把 `CrashFileLogger`/`DiPlayApplication`/
     `BootReceiver` 强制留在**主 dex**，确保 `attachBaseContext` 在 MultiDex.install 前就能调用处理器。
  5. 启动 Toast 改为指向公共路径 `/sdcard/DiPlay/crash-last.log`。
- 验证（JDK17）：`:mobile:compileDebugKotlin` BUILD SUCCESSFUL（仅 deprecation 警告）；
  `:mobile:processDebugManifest` 通过且合并 manifest 含 `WRITE_EXTERNAL_STORAGE`。
- **取回方式（针对 launcher 死/死循环）**：车机连电脑选"传输文件(MTP)"，拷
  `/sdcard/DiPlay/crash-last.log`（和 `crash-<时间戳>.log`）即可。
  **若两路径都没有任何文件** ⇒ 基本可判定是 native/system 级崩溃（Java handler 抓不到），
  只能换一台**可 adb** 的同型号车机复现，用 `adb bugreport` / `ndk-stack` 解析。
- 防 boot loop 恢复建议（未实现，待用户确认）：连续 N 次启动早期崩溃时写 `SAFE_MODE` 标记，
  下次启动跳过 CarPlay/USB/媒体等高风险初始化，给用户留出恢复窗口。

## Bug fix: attachBaseContext 前置 install 引入 API17 NPE（致命启动崩溃）
- 现象：API17 车机 `FATAL EXCEPTION: main` → `Unable to instantiate application DiPlayApplication`，`Caused by NullPointerException` @ `ContextWrapper.getApplicationContext(:109)`，PID 收到 SIG:9。
- 根因：上一轮把 `CrashFileLogger.install(this)` 提到 `DiPlayApplication.attachBaseContext` 的 `super.attachBaseContext(base)` **之前**（`DiPlayApplication.kt:18`）；install 内 `CrashFileLogger.kt:30 context.applicationContext` 在 mBase 尚未赋值时访问。API17(dalvik 4.2.2) 的 `ContextWrapper.getApplicationContext()` 无空守卫（直接 `mBase.getApplicationContext()`）→ mBase 为 null → NPE。本机日志正是包名 `com.shihab.diplay.hudtest`（API17 测试机），印证时序问题。
- 修复：`CrashFileLogger.kt:30` 改为 `val appContext = if (context is Application) context else context.applicationContext`（Application 自身即 application context，attachBaseContext 期间 mBase 未就绪也不触碰）。`super` 顺序与 install 前置逻辑保留不动（仍能抓 multidex 早期崩溃）。
- 回归检查：单测 `CrashFileLoggerTest.kt` 的 `RuntimeEnvironment.getApplication()` 也是 Application → 走同一分支，不影响；`writeCrash`/`lastCrashFile`/`allCrashFiles` 均在崩溃发生时（mBase 已就绪）调用，无影响。

## API 17 兼容扫除（第二轮）：Drawable/View tint 家族
- 现象：首页→设置页已通，点击"外观"类目崩 `NoSuchMethodError: android.graphics.drawable.Drawable.setTint` @ `DiPlayActivity$SettingButton.setText(DiPlayActivity.kt:4279)`（API 21）。根因同上轮：dalvik 把缺方法指令替换成 throw 桩，一执行即 NoSuchMethodError。
- `UiCompat` 新增 3 个助手（`internal object`，已加 `@Suppress("DEPRECATION")` 消掉自身降级路径的 deprecation 告警）：
  - `tint(drawable, color)`：≥21 用 `setTint`，否则 `setColorFilter(color, SRC_IN)`。
  - `setBackgroundTint(view, list)`：≥21 用 `view.backgroundTintList`，否则 `background?.mutate()?.setColorFilter(list.getColorForState(intArrayOf(), TRANSPARENT), SRC_IN)`（注意 `ColorStateList.defaultColor` 是 API 23，不能用）。
  - `setOutlineProvider(view, clip) { provider }`：**provider 必须以 lambda 传入**，≥21 才调用；`ViewOutlineProvider` 类在 API17 不存在，外部直接 new 会导致子类链接失败。
- 改动点：`DiPlayActivity.kt:4279`、`ClusterTurnCardView.kt:224`（setTint→UiCompat.tint）；`CarPlayHostActivity.kt` 的 `backgroundTintList`×5（save/danger/openSettings/X 按钮/EditText）→UiCompat.setBackgroundTint；`CenterMapOverlay.kt:135` 的匿名 `ViewOutlineProvider` 改为在 `UiCompat.setOutlineProvider` 内延迟构造 —— 它正是上一轮日志里 `Unable to resolve superclass of CenterMapOverlay$show$card$1$1 / Link of class failed` 的根因（ViewOutlineProvider 是 API 21，子类链接失败→new-instance 被替换为 throw 桩）。
- 确认安全无需改：`BydStandaloneHudOutput.available()`/`diagnostics()` 的 `signingInfo`/`longVersionCode`(API28) 已被 `SDK_INT < 28` 提前返回 + `runCatching` 双重保护；`StandaloneHudDemoActivity.validateTarget()` 的 API28 行在 fingerprint check 之后，够不到；`Typeface.create(String,int)` 是 API 1；`CarPlayVideoActivity.setColorFilter` 是 API 1。
- 验证：`:common:compileDebugKotlin` **BUILD SUCCESSFUL**，UiCompat 相关告警 0 条；全仓库生产代码已无直连 `setTint(`/`backgroundTintList =`/`outlineProvider =`（仅 UiCompat 内部保留，均带守卫）。
- **结论修正：`getSystemService(Class)` 批量不是纯机械替换**，需两件事：
  1. 对 API17 不存在的类必须加版本守卫（否则 `as?`/`instanceof` 的 class 引用被 dalvik 换成 throw 桩）：BluetoothManager(18)、AppOpsManager(19)、UsageStatsManager(21)、TetheringManager(30)、LocaleManager(33)。已有的安全例子：`AppLocale` 全在 `>=33` 守卫内、`DiPlayBluetooth`/`HomeScreenMonitor` 在 `runCatching` 内。
  2. `shared/main` 多个类被 Mockito `when(context.getSystemService(X::class.java))` stub（`ExistingWifiManagerTest`、`CarPlayBonjourDualStackTest` 等），改字符串重载会使 mock 失配 → 必须同步改测试。
- **真实崩溃风险点（未修，待确认）**：`DiLink51ClusterMonitor.kt:54`（UsageStatsManager）与 `:82 hasAccess`（AppOpsManager）**不在** `runCatching` 内，外层仅 `catch (RuntimeException)`，而 `NoSuchMethodError` 是 `Error` → 会直接崩。`HomeScreenMonitor`/`DiPlayBluetooth` 同类调用有 `runCatching` 保护，只静默失效。
