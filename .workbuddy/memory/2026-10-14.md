# 2026-10-14 DiPlay 蓝牙第六轮：isEnabled=false 为真 + 配对库为空 → 双蓝牙架构

## 决定性证据（0.2.19-api17 截图，权限修复已生效）
- 弹「配对 iPhone」诊断：isEnabled=false、已配对设备数=0（无异常行→bondedDevices 读取成功返回空）、connectedIphone 未探测到。
- 结论：Android 侧适配器真关 + 无配对记录；iPhone「已连接 MyLink Captive」是原厂蓝牙模块——双蓝牙架构（此前第五轮已预判）。

## 本轮改动
1. BluetoothCompat.tryEnable(adapter)：反射调隐藏 API enable()（需 BLUETOOTH_ADMIN，已声明），catch 只列 API 1 异常（防 API 17 VerifyError）。
2. 两个诊断弹窗（choosePhone 空候选分支 + showTurnOnBluetoothDialog）加「适配器名称/适配器地址」两行——与系统蓝牙设置显示的车机名（MyLink Captive）比对即可当场判定双蓝牙。
3. 「打开蓝牙」按钮改为：先 tryEnable → 成功受理则 toast + 2s 后自动重跑 choosePhone()；失败才跳系统蓝牙设置。

## 复验判定
- 若 enable 受理后 isEnabled 变 true 且列表仍空 → 需在系统蓝牙设置里把 iPhone 与 Android 适配器重新配对一次。
- 若适配器名称 ≠ MyLink Captive → 双蓝牙坐实，首选路径是方案C实验开关（docs/实验性方案C开关（无蓝牙引导无线连接）开发设计文档.md，待用户确认 §10 策略后落地）。

# 2026-10-14 有线 CarPlay 第七轮：claimProbe=[0=ok,1..5=fail] → 内核 actconfig 未刷新

## 决定性证据（最新 APK 截图）
```
usbmux pre-claim config=6 id=6 index=5 active=6 candidates=[1] ...
usbmux claim refused iface=1 endpoints=2
ERROR Android could not claim any USBMUX interface
      (candidates=[1] active=6 claimProbe=[0=ok, 1=fail, 2=fail, 3=fail, 4=fail, 5=fail…])
```
- 只有 **0 号**接口可 claim，1 号起全 fail。USBMUX(ff.fe.02, vendor-specific, 无内核驱动)也被拒 → 它不在内核 actconfig 里。
- 结论：**iPhone 已切到 6（GET_CONFIGURATION=6），但 Linux 内核 dev->actconfig 仍停在切换前的 1 接口配置**。

## 根因
- API 17-20 没有框架 `setConfiguration(UsbConfiguration)`(API 21+)。此前用**原始 SET_CONFIGURATION 控制传输**：只到设备、内核不刷新 `actconfig`。
- `USBDEVFS_CLAIMINTERFACE` 按 `actconfig` 解析接口号 → 新配置里的接口全部 ENODEV。
- LIVI 在 Linux 上是 `fs::write(sysfs bConfigurationValue, "6")`（内核级）。等价手段 = `USBDEVFS_SETCONFIGURATION` ioctl。

## 本轮改动（仅框架层，未碰爬虫/KSPlayer）
1. **新增 JNI 模块 `xcertplay_usbconfig`**：`shared/src/main/jni/usb_config_jni.c` + `Android.mk` 条目。
   - `setConfiguration(fd, value)` = `USBDEVFS_SETCONFIGURATION`；`detachKernelDrivers(fd)` = `USBDEVFS_DISCONNECT`；返回 0 / 负 errno。
2. **新增 `transport/UsbConfigurationKernel.kt`**：native 桥（`System.loadLibrary` 失败静默降级为 -1）。
3. **新增 `transport/UsbConfigurationSwitch.kt`**：纯逻辑，内核 ioctl 优先；fd<0 或 ioctl!=0 才回退控制传输；含 `diagnostic(...)`。
4. **`IphoneUsbHost.selectConfiguration`**：`setConfiguration` lambda 改调 `switchConfiguration(connection, device, configuration, target)` —— `connection.fileDescriptor`（public API 12）→ `detach + SET_CONFIGURATION(target)` → 成功即返回，否则 `UsbDescriptorCompat.selectConfiguration` 兜底。
5. 单测 `UsbConfigurationSwitchTest`（5 例，全过）。

## 验证
- `:mobile:assembleDebug` **BUILD SUCCESSFUL**；`libxcertplay_usbconfig.so` 已打入 arm64-v8a/armeabi-v7a/x86/x86_64。
- APK：`mobile/build/outputs/apk/debug/mobile-debug.apk`（21 MB，sha1 `6ea24e5d8547fae67ecdf1c9333aad04e9933d36`）。

## 复验判定（看屏幕诊断）
- 预期：`usb config kernel SET_CONFIGURATION(6) fd=… detach=0 result=0 … ok=true` → 随后 `claimProbe` 多号 =ok → `usbmux claimed iface=… attempts=…` → 进 iAP2/NCM。
- `result=-16`(EBUSY) → 仍有接口绑驱动，需更强 detach（USBDEVFS_DISCONNECT 被拒时走 per-interface 强制 claim）。
- `fd=-1` → getFileDescriptor 取不到（不太可能）。
- `result=-5`(EIO)/`-19`(ENODEV) → 内核拒绝切配置，需查是否有其他 usbfs 持有者。
