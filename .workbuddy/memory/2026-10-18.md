## 有线 CarPlay 卡点定位（NCM 桥返回后、wired USBMUX host opened 之前）
- 卡点确认：截图停在 `ncm open: returning bridge (claimed 2 interface(s))`，其后无任何 `wired USBMUX host opened`。
  链路 `openDataPaths`(:2328) → `openNcm`(:2338 二次 openDevice) → `runStack`(:2370) → `Iap2UsbMuxHost.open` → `begin()`(:109) 的 `pipe.write(version, 60000)` 此前**无任何前置日志**，故卡死即在该写。
- 两候选根因：(a) 双 UsbDeviceConnection 冲突——`openIap2UsbSession` 开连接 A(USBMUX iface1)，`openNcm` 再 `openDevice` 开连接 B(NCM iface3/4)；C140A API17 内核二次 open / SET_INTERFACE 可能重置连接 A 的 bulk-OUT 管道；(b) iPhone 不回 USBMUX 版本包。
- 已落地诊断（未提交，待构建机出包复验）：
  - `Iap2UsbMuxHost.begin()` 加 4 个 `onDiagnostic` 触点：handshake begin / wrote X bytes / waiting for version reply(每2s) / version accepted；`open()` catch 补 `usbmux handshake failed:`。
  - 写看门狗线程 `usbmux-write-watchdog`（28s，早于 HANDSHAKE_TIMEOUT），超时未返回即报「possible kernel bulkTransfer stall on USBMUX bulk-OUT」。
  - `HANDSHAKE_TIMEOUT_MILLIS` 60s→30s（诊断构建，量产恢复 60_000L）。
  - `Iap2UsbSession.probeControlChannel()` 新增：NCM 二次 open 后向连接 A 发无害 GET_STATUS(recipient=设备,1s超时)，`runStack` 在开 USBMUX 前打 `wired USBMUX session probe after NCM open: ok/unexpected/failed`，用于区分「连接A被双连接破坏」与「iPhone不回包」。
  - `UsbMuxIssue100RegressionTest` 两处 `assertEquals(size==2/4)` 放宽为 `.any{contains(...)}`（begin 现多输出3条握手诊断）。
- 复验判据（看可滚面板）：
  - probe=ok 但无 `wrote 20 bytes` → 写卡死 → 看门狗28s报警 → 双连接破坏 或 iPhone NAK(走单连接重构)。
  - probe=ok 且 `wrote` 出现但停在 `waiting for version reply` → iPhone 不回版本包。
  - probe=failed/unexpected → 确证双 UsbDeviceConnection 冲突，需重构为单连接（设计文档待出）。
- 下一步：构建机 `./gradlew :mobile:assembleDebug` 出包 → 车机原口原线重插 → 截图可滚面板末段按上表判因。

## 屏幕实时日志 → 诊断报告同步（已实现并验证）
- 需求：真机看不到 logcat，只能截图屏幕「实时日志」面板；要求面板每一行都进 `diplay.log`，导出报告可直接替代截图。
- 根因（CarPlayHostActivity.onDebugLog，原 5270-5303）：面板写入 `usbDiagLines` 无门禁，但落盘走 `runOnUiThread` + 两层门禁——`controllerGeneration != restartGeneration`（旧控制器）与 `menuOpen`（设置菜单展开）都会**静默丢行**；另外 CONNECTION_DIAGNOSTIC 前缀分支单独走异步队列，其余行走 `appendLog`。
- 改法：redact 一次后**无条件** `AsyncDiagnosticLog.append(diagnosticLog ?: sessionLog, redacted)`（不阻塞传输/网络回调线程），再做面板写入；前缀分支改为直接 return（已落盘），普通分支只保留 `DisplayDiagnosticSnapshot.record`，不再重复写文件。
- 导出侧（DiPlayActivity.diagnosticReportText）在开头加 `AsyncDiagnosticLog.awaitIdle(DIAGNOSTIC_FLUSH_TIMEOUT_MILLIS=1000)`，避免报告比面板少最后几行（报告本就在后台线程生成）。
- 测试（CarPlayConnectionDiagnosticLogTest，4/4 通过）：原用例 `oldTeardownEvidenceSurvivesWithoutAcceptingOtherOldControllerLogs` 断言的「旧控制器普通行不得进文件」与新契约冲突，改名 `...WithoutTheOldControllerTakingOverTheSession` 并改为断言**进文件**（拒绝的是会话状态不是日志）；新增 `anOpenMenuNoLongerDropsTheLiveLogFromTheReport`、`everyLivePanelLineAlsoReachesTheReport`（面板与文件双断言）。
- 验证：`:common:compileDebugKotlin` SUCCESS（无新增警告）；`:common:testDebugUnitTest` 相关类 4+16 全绿；`:mobile:assembleDebug` 出包 `mobile-debug.apk` 21M。
- 未提交：CarPlayHostActivity.kt / DiPlayActivity.kt / CarPlayConnectionDiagnosticLogTest.kt 三处改动（分支 `port/wave14-increment`）。

## 构建故障：KotlinFrontEndException / CodecCompat.class FileNotFoundException（已修复）
- 现象：`:common:compileDebugKotlin` 抛 `KotlinFrontEndException: Exception while analyzing expression in (4713,23)`，根因为
  `java.io.FileNotFoundException: common/build/tmp/kotlin-classes/debug/com/shilapi/xcertplay/CodecCompat.class`，
  栈顶为 `KotlinCliJavaFileManagerImpl.findClass` → `LazyJavaPackageScope.getContributedClassifier`（经 IntelliJ VFS `CoreLocalVirtualFile.contentsToByteArray`）。**不是源码问题**（release 变体可正常编译）。
- 证据：`kotlin-classes/debug` 被清空为 0 个 class（release 仍有 963 个），而 `build/kotlin/compileDebugKotlin/{cacheable,classpath-snapshot,local-state}` 残留旧增量状态；
  同时机器上并存两个 GRADLE_USER_HOME（`~/.gradle` 与 `/Users/chengshengru/Apps/gradle-9.2.1`），各起一个 Gradle 7.6.4 daemon + 一个 KotlinCompileDaemon，
  构建日志出现 `w: Detected multiple Kotlin daemon sessions at kotlin/sessions` —— 两个守护进程共用同一 `common/build`，输出目录被一方删除、另一方的 VFS/增量索引仍认为 CodecCompat.class 存在。
- 处理（已执行，编译通过）：`./gradlew --stop`；`GRADLE_USER_HOME=/Users/chengshengru/Apps/gradle-9.2.1 ./gradlew --stop`；kill 残留 GradleDaemon/KotlinCompileDaemon（无 daemon 存活后重建，输出目录重新生成 973 个 class）。
- 复发防护：不要用两个 GRADLE_USER_HOME 同时对同一工程构建；报此类错误先 `--stop` 全部 daemon 再重建，必要时删 `common/build/kotlin` 与 `common/build/tmp/kotlin-classes/<variant>`。
- 注：沙箱禁止写入 `~/Library/Application Support/kotlin/daemon/`（tsmarker 临时文件删不掉，已堆积 300+），不影响编译但会让会话标记累积。

## 崩溃修复：长按可选文本 → InflateException/StringBlock.get 越界（API 17）
- 现场：`com.shihab.diplay.hudtest` 0.2.20-api17-hud-test，2026-10-13 00:02:33。
  `TextView.performLongClick → Editor.startSelectionActionMode → Editor$ActionPopupWindow.initContentView`
  inflate 框架 `text_edit_action_popup_text` → `TextView.<init>` 读 `fontFamily` → `TypedArray.getString`
  → `XmlBlock$Parser.getPooledString` → `StringBlock.get` 抛 `ArrayIndexOutOfBoundsException: length=15; index=2002`。
- 根因：**API 17-20 主题里写了字符串型属性 `android:fontFamily="sans"`**（`common/src/main/res/values/themes.xml` 4 处）。
  框架弹窗布局用 App 主题 inflate，`TypedArray.loadStringValueAt` 把 App 资源表的全局字符串索引（2002）当成框架布局
  XmlBlock 自身池（15 条）的索引 → 越界。属 AOSP 4.x 已知缺陷（SO 多例：`sans-serif-light`/`sans-serif-condensed`/`textAlignment`）。
  Lollipop+ 修复，故只在默认（非 v21）配置里发作。
- 修复：从 `values/themes.xml` 的 4 个 style（Theme.Xcertplay / Dialog.Dark / Light / Dialog.Light）删除 fontFamily，
  v21 保留（+注释说明原因）。Holo 默认字体本就是 sans-serif，API 17-20 观感不变。
- 验证：`:mobile:processDebugResources` 通过；`aapt2 dump resources` 成品 `mobile-debug.apk` 中 `style/Theme.Xcertplay`
  默认配置 size=2 无 `0x010103ac`，v21 配置仍有 `"sans"`；`./gradlew :mobile:assembleDebug` BUILD SUCCESSFUL 零 warning。
- 规律（写进约束）：**API 17-20 的默认 `values/themes.xml` 里禁止任何字符串型 item**（fontFamily / textAppearance 间接带
  fontFamily / 其他 literal string），需要就放 v21。Widget 级 XML 属性安全（索引来自该布局自身池），主题级才致命。

- 同类复发（本次）：`IntToIntBtree$BtreePage.syncWithStore` + `IndexOutOfBoundsException` + `Gradle build daemon has been stopped: stop command received` → 直接**重跑同一命令**即恢复（无需删 build 目录）；构建结束时 stderr 出现 `[sandbox] ... kotlin-daemon...run (file-delete)` 属沙箱拦截守护进程临时清理，**不算构建失败**，以 stdout 的 `BUILD SUCCESSFUL` 为准。
