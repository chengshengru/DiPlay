  - `Iap2UsbMuxHost.begin()` 加 4 个 `onDiagnostic` 触点：handshake begin / wrote X bytes / waiting for version reply(每2s) / version accepted；`open()` catch 补 `usbmux handshake failed:`。
  - 写看门狗线程 `usbmux-write-watchdog`（28s，早于 HANDSHAKE_TIMEOUT），超时未返回即报「possible kernel bulkTransfer stall on USBMUX bulk-OUT」。
  - `HANDSHAKE_TIMEOUT_MILLIS` 60s→30s（诊断构建，量产恢复 60_000L）。
  - `Iap2UsbSession.probeControlChannel()` 新增：NCM 二次 open 后向连接 A 发无害 GET_STATUS(recipient=设备,1s超时)，`runStack` 在开 USBMUX 前打 `wired USBMUX session probe after NCM open: ok/unexpected/failed`，用于区分「连接A被双连接破坏」与「iPhone不回包」。

## 18:47 有线复验（新日志）：握手已通，失败点前移到 lockdown 配对
- 进展：10-17 的「bulk-OUT 写卡死」假设被推翻——本次 `usbmux handshake wrote 20 bytes in 0ms` + `usbmux version accepted: 2` 出现，且 NCM 二次 open 后的 `probeControlChannel` = `ok transferred=2`。说明双 UsbDeviceConnection 没破坏 USBMUX 收发。
- 新失败点：`stage=Pairing` 之后（`loadPairRecord()==null` → 首次配对）无任何响应，随后管道被判死。
- 本次 5 次尝试的三种错误签名（全部来自 `Iap2UsbSession.failSession`，IphoneUsbHost.kt:803-804）：
  1. `Android could not cancel timed out USBMUX read request`（18:47:41.7 / 09:04:40.0 / 09:06:42.4）→ `drainTimedOutRead`(:777-801) 里 `request.cancel()==false` + drain 1s 无回收。
  2. `Android could not queue USBMUX read request (timeoutMs=41284 …)`（09:05:11.2）→ UsbReadQueuePolicy 16K→8K→4K→2K 全被拒，端点已废。
  3. `Android returned no USBMUX read request`（09:05:38.0）→ wait 线程 `requestWait()` 返回 null（连接进入错误态）。
- 判定：会话死亡不是协议错误，而是「手机静默 → 1s 空闲读超时 → cancel 赌局输掉 → 整个会话判死」。`Iap2UsbMuxHost.open(usbSession, onDiagnostic=…)` 用默认 `readTimeoutMillis=1000`（Iap2UsbMuxHost.kt:342 / CarPlayController.kt:2378），即每一秒都赌一次 cancel。
- 潜在必炸点：`LockdownPairingClient.MAXIMUM_STEP_TIMEOUT_MILLIS=5000`(:225) 同时作用于 Pair 请求，而 Pair 要等 iPhone 上人工点「信任」→ 必然超时。重试退避只有 2s/4s，手机上反复弹框、来不及点。
- 诊断盲区：mux 帧/TCP 控制帧只写 `Log.i("xcertplay-usb")`（Iap2UsbMuxHost.kt:88/206-210/275），不进 onDiagnostic → 报告里 18:47:32.455→41.755 有 9.3s 完全黑箱。
- 页面「自动退出」：日志在 18:47:45.079 的 `ncm open: claiming control iface=3 force=true`(NcmUsbBridge.kt:494) 之后**硬截断**，无 teardown / 无 Activity destroyed / 无 Java 崩溃记录 → 进程被硬终止（native 崩溃或被杀）。`reconnectAfterLoss`(CarPlayHostActivity.kt:5862) 无次数上限，代码路径本身不会退出页面。

  Lollipop+ 修复，故只在默认（非 v21）配置里发作。

## 有线 CarPlay 卡点修复：USBMUX 读请求生命周期 + 配对对话框同连接重试
- 现场（DiPlay-20261018-184756-614.txt）：有线链路 USB 枚举/0x52 重枚举/配置切换/USBMUX claim/NCM claim/双连接探针/版本握手全部通过，
  卡在 `stage=Pairing` → `loadPairRecord()=null` → 之后 9.3s 无输出 → 5 次尝试三种签名都出自旧 `Iap2UsbSession.read` 的
  cancel+drain 失败（"could not cancel timed out USBMUX read request" / "could not queue ... read request" / "returned no ... read request"）。
  用户在 iPhone 上点了"信任"仍无用；进程最终在 `ncm open: claiming control iface=3` 处消失并退回 DiPlay 主页（车机无 adb）。
- 根因 1（进程猝死）：`Iap2UsbSession.read` 超时后 `request.cancel()` + `finally request.close()`。厂商内核拒绝 cancel 时 URB 仍在 usbfs 队列，
  close() 释放 native 缓冲 → 内核完成回调写已释放内存 → SIGSEGV（无 Java trace、日志戛然而止、Android 回到栈内的 DiPlay 主页）。
- 根因 2（配对失败）：`LockdownPairingClient` 收到 `PairingDialogResponsePending` 后**断开重连**再发 Pair，iPhone 侧配对会话随 TCP 连接作废，
  用户点的"信任"永远回不到宿主；且 step 超时 5s 直接套在 Pair 上。
- 修复（shared/transport）：
  1. `IphoneUsbSession` 改用 NCM 桥同款模型：`pendingRead + pendingReadBuffer + readQueued` 复用同一条 URB，超时只返回 null，**不 cancel、不 close、不 failSession**；
     `close()` 顺序改为 cancel → connection.close() → request.close()。
  2. `LockdownPairingClient`：Pair 在**同一条连接**上循环重发（pending 期间 1s 间隔），只有 `IphoneUsbException` 传输错误才换连接（上限 5 次）；
     超时拆分：传输步骤 20s、Pair 响应 120s、总预算 5min；新增 `onDiagnostic` 逐步耗时（connect/SetValue/GetValue/Pair/pending）。
  3. `Iap2UsbMuxHost`：`connect()` 记录 SYN-ACK 是否到达；TX/RX 帧摘要（端口/标志/长度，不含载荷）前 64 帧进会话报告；reader 线程收尾原因落日志。
  4. UI：配对阶段提示"请在 iPhone 上点信任"（pairing_with_iphone_trust_hint，values / zh-rCN / zh-rTW）。
- 回归测试：重写 `UsbmuxTimedOutReadTest`（超时保留 URB、重复超时不断会话、空闲读不释放请求对象），`UsbReadQueueCompatibilityTest` 的
  shadow 增加 `requestCloses` 计数（close 只在会话关闭时发生一次）。`:shared:testDebugUnitTest` 除 `AirPlayDualListenerTest`（沙箱 IPv6 环境性
  SocketTimeoutException，与本次改动无关）外全绿；`:mobile:assembleRelease` BUILD SUCCESSFUL → mobile/build/outputs/apk/release/mobile-release.apk。
